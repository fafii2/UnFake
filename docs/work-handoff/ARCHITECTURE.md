### Proposed SRS display mapping

Keep the v1 machine-readable verdict values and map them to display labels in a later extension phase. The operational definitions below are design proposals based on the notebook's cited labels. The exact SRS definitions and the treatment of no evidence still need direct review.

| API response | Proposed display | Evidence rule |
| --- | --- | --- |
| `completed` with `supported` | Credible | Directly applicable evidence supports the claim as stated. |
| `completed` with `contradicted` | Contradicted | Directly applicable evidence contradicts the claim as stated. |
| `completed` with `mixed` | Questionable, conflicting evidence | Relevant evidence supports and contradicts the same claim after scope and dates are checked. |
| `completed` with `insufficient_evidence` | Insufficient evidence notice | Abstain when evidence is absent, incomplete, or too weak. Confirm whether the SRS display groups this state under Questionable. |
| `triage_rejected` or an error | Triage or error notice | No evidentiary verdict. |

## Components and data flow

| Stage | Design and integration point |
| --- | --- |
| Capture | `extension/background/service-worker.js` receives `info.selectionText` for highlights. Crop uses explicit tab access, viewport capture, and offscreen canvas processing. The existing OCR review shows extracted text and recognition confidence. Only submitted text crosses the API boundary. |
| Normalize and triage | Reuse `extension/shared/claims.js` and backend preprocessor/triage services. Strip interface clutter while preserving names, quantities, units, dates, quotes, and negation. Reject empty or unsupported requests. Return a reason for opinions or incomplete assertions without an external call. Preserve the submitted and normalized text only in request memory. |
| Derive evidence queries | Start with an exact reviewed claim key, including reviewed translations. For other claims, form bounded search queries from the factual assertion and its entities, timeframe, and quantities. Remove unrelated identifiers. Withhold external search when the necessary text contains private data. Preserve the meaning of bilingual phrases and record any query translation in memory for relevance checks. |
| Retrieve and normalize | Use existing SQLite and its FTS5 index. Add optional local embeddings after measured gains and version each vector by model. Read a small candidate set per source so archive results cannot crowd out all live results. Evidence adapters normalize canonical URL, publisher, title, publication or effective date, retrieval time, relevant excerpt, and source type. Persist verified public archive records through reviewed imports. Discard request-only provider output after completion. |
| Compare evidence | Match the same actor, assertion, date, quantity, negation, and scope. A quote attribution and the truth of the quote are separate assertions. Use document revisions and official dataset metadata for numeric claims. Group syndications by original reporting and treat a circular citation as one evidence family. Give relevant primary records priority within their scope, then seek independent corroboration for disputed or consequential assertions. |
| Evaluate and render | Reuse the archive's original reviewed rating for exact claims with matching context. Rank and label other sources as supporting, contradicting, or contextual. Validate the verdict against the supplied evidence IDs and show publisher, date, and clickable canonical link. Show which retrieval lane failed and display a readable insufficient-evidence state when direct evidence is unavailable. |

Start with FTS5 and a reviewed archive. The current small-corpus cosine scan can remain until measurements justify HNSW or a database change. The algorithms reference discusses Aho-Corasick and Levenshtein. Use them only if comparative tests show better lexicon matching or OCR tolerance without changing claim meaning. Fuzzy matches and embedding scores rank candidates. A reviewed rating or directly relevant evidence determines stance.

## Verification and confidence

Use deterministic checks for verifiability, exact archive matches, citation integrity, and minimum evidence. For new claims, the proposed classical baseline is a local Decision Tree on independently labeled claim/evidence pairs. Features can cover lexical and entity alignment, date and quantity agreement, negation, retrieval score, and source type. Compare against a simple lexical baseline and, if useful, logistic regression. Train using real sources and independently reviewed labels. Split by claim family, publisher reuse, and time to limit leakage. Report per-class precision and recall, macro F1, confusion matrix, and abstention coverage. Check English, Filipino, and Taglish separately. Thresholds require held-out measurements. The model's class output is a signal for the evidence gate. Publisher reputation and search ranking alone cannot establish stance.

The existing Gemini assessor is an optional comparison for structured stance and explanation on approved public test cases. Keep the prompt constrained to supplied snippets. Validate schema, unique known source IDs, exact quote provenance, and consistency between the verdict and evidence stances. Use a deterministic explanation or abstain after provider failure. Validate material factual statements against the retrieved records and keep model output inert in the renderer. A supported or contradicted verdict requires directly applicable evidence. Use mixed only when both stances address the same assertion and the conflict remains after resolving dates and scope. Use insufficient evidence for partial snippets, weak matches, unresolved entity/date ambiguity, or no usable sources. Report expired or superseded evidence as context.

The notebook cites FR-07 for a displayed 0 to 100 percent confidence score and describes text alignment and domain credibility as scoring features. An exact approved formula or validation protocol was unavailable. Keep `confidence: null` and `confidence_kind: unavailable` through Phase 3 and for abstentions. In Phase 5, fit a calibration mapping to observed correctness using data separate from model training and final evaluation. Use the validated score in the API as a value between 0 and 1. The UI converts that value to a percentage for eligible results. Report reliability by score range with sample counts, calibration error or Brier score, and abstention coverage. Invalidate the artifact when the model, features, source policy, or claim distribution changes materially. OCR recognition confidence stays in the client and describes transcription quality only.

## API and runtime contract

Reuse the current [API contract](../API_CONTRACT.md), `backend/api/schemas.py`, and `backend/main.py`. Treat the schema and handlers as authoritative where older examples disagree.

| Interface | Contract and compatibility |
| --- | --- |
| `GET /api/v1/health` | Returns `service`, `version`, `status`, `live_search_configured`, `evaluation_configured`, and `embedding_provider`. Configuration flags describe availability of settings. They do not prove provider connectivity. Keep the existing popup offline state and avoid exposing credentials. |
| `POST /api/v1/verify` | JSON request `{"claim":"The submitted assertion","input_type":"text"}`. Use `image_ocr` for reviewed screenshot text. The contract accepts a trimmed string of 1 to 5,000 characters. Backend revalidation also rejects text that normalizes to noise. No screenshot, browsing URL, or history field is needed. Cap the encoded request size before parsing for a hosted pilot. |
| HTTP 200 | `completed` returns a verdict, explanation, evidence, `confidence_kind`, `confidence`, `evaluation_method`, `triage`, `warnings`, `timings`, `processing_time_ms`, and `original_claim`. Evidence items retain `id`, `title`, `publisher`, `published_date`, `source_url`, `snippet`, `relevance`, and `source_type`. `triage_rejected` has null verdict and empty evidence. `insufficient_evidence` is a completed assessment and may include contextual evidence. The existing response enum represents provider retrieval as `web_search`. |
| Errors and delivery | Preserve the `{status,error_code,message}` envelope for 422 validation, 504 deadline, and 500 internal error. For a future authenticated pilot, define 401 and 429 with a bounded retry hint. Within the browser, keep the loading state, offline error, and initiating-tab/request pairing. Check that rapid retry and navigation do not show stale results. |
| Deadline | Current defaults are 3 s for popup health, 12 s per provider HTTP client, 25 s for server verification, and 28 s for the extension request. In Phase 3 retain these as guardrails. In Phase 4 measure per-stage p50 and p95, enforce an absolute deadline across retrieval and evaluation, and reserve response time for fallback. A single failed provider should produce a warning and usable partial results when available. |

## Deployment, privacy, and access

The recommended pilot runs Python FastAPI on the user's machine at `127.0.0.1:8000` with the existing `http://localhost:8000` client URL. Verify Windows localhost resolution and Chromium host permissions in Phase 3. SQLite stores reviewed evidence, source and rights metadata, and optional embeddings. Retain publication and retrieval dates, original rating and canonical source, correction history, and model identifiers. The importer already derives record identity from source URL plus normalized claim. Preserve that identity, test idempotent reimports, and keep different claims from the same article distinct in storage. Review URL canonicalization and prevent result deduplication by URL alone from hiding a distinct relevant claim. Add rights and correction metadata through a compatible migration only if existing records need those fields. Keep offline setup and the sample verdict reproducible. Use the pins in [backend requirements](../../backend/requirements.txt) and the variables in [the environment template](../../backend/.env.example). Override the template host with a loopback bind for the pilot, leave provider keys empty, and verify FTS5 support. Local embeddings use [separate optional dependencies](../../backend/requirements-semantic.txt).

Keep only the required Manifest V3 permissions. Restrict the loopback bind and validate intended callers with an explicit extension origin policy. CORS is not authentication. Before exposing a shared API, use TLS and scoped, revocable pilot access with rate and concurrency limits. Keep provider keys server-side with local environment settings or a deployment secret store. Never bundle secrets in the extension. Reject unsafe URL schemes. For later publisher fetches, deny private and loopback destinations, validate DNS and redirects, and bound content size. Retain operational counters and timings without claim text, user identifiers, or image data. Review provider input, downstream retention, and disclosure before enabling external queries. The [National Privacy Commission's Data Privacy Act text](https://privacy.gov.ph/data%20-privacy-act/) supplies the transparency, purpose, and proportionality context.

Supabase is optional for a later shared evidence archive. If concurrent editorial work justifies it, use managed PostgreSQL for approved public evidence and pgvector only if measured vector scale warrants it. Keep the DB off the browser request path. For an exposed data API enable RLS on exposed tables, verify default denial, and restrict write access to curators or a server-side job. Supabase Auth is a possible later curator identity service. Object Storage has no role in the screenshot flow. Store service credentials in the Python host secret store, or in Supabase Function secrets if a separate Edge Function is approved. A service-role key bypasses RLS and stays server-side. Account access was unverified because Chrome reached the dashboard sign-in page.

Supabase Edge Functions are Deno/TypeScript with hosted limits. They cannot host the existing Python FastAPI process as-is. The free DB plan can pause after inactivity. Retain local FastAPI for the pilot. If shared verification is later approved, host FastAPI on a separate Python-capable service after reviewing budget, data handling, and uptime. See [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [pgvector](https://supabase.com/docs/guides/database/extensions/pgvector), [Function secrets](https://supabase.com/docs/guides/functions/secrets), [Edge runtime](https://supabase.com/docs/guides/functions/quickstart), [limits](https://supabase.com/docs/guides/functions/limits), and [pricing](https://supabase.com/pricing).
